#+title: dbx-el — a Databricks workbench for Emacs

dbx-el brings Databricks into Emacs 30 (commands and options use the
=dbx-= prefix): a SQL editor with results as Org
tables, jobs and runs with text pages (status glyphs, duration bars, a
task × run matrix), clusters and SQL warehouses, Declarative Automation
Bundles with Graphviz graphs, Lakeflow Declarative Pipelines with dataset
graphs, and a Python REPL running on Databricks Connect.  Every picker is
plain =completing-read=, so it works with Vertico, Helm, Ivy, Icomplete,
Consult, Marginalia and Embark.

* Requirements

| What                    | Needed for                         | Notes                                                    |
|-------------------------+------------------------------------+----------------------------------------------------------|
| Emacs ≥ 30.1            | everything                         | plus transient ≥ 0.7, which ships with Emacs 30           |
| =databricks= CLI ≥ 1.25 | everything except the Python REPL  | the control plane; auth comes from =~/.databrickscfg=    |
| uv                      | Python REPL, run-file              | the only Python-side requirement; it also provides Python |
| Graphviz =dot=          | graphical graphs (optional)        | without it graphs are shown as text trees                |

* Installation

From Git with the built-in package-vc (the package name must be given,
because the repository name differs from the package name):

#+begin_src emacs-lisp
(package-vc-install '(dbx-el :url "https://github.com/SemyonSinchenko/dbx-el.git"))
#+end_src

or with =use-package= (Emacs 30):

#+begin_src emacs-lisp
(use-package dbx-el
  :vc (:url "https://github.com/SemyonSinchenko/dbx-el.git" :rev :newest)
  :bind-keymap ("C-c d" . dbx-command-map)
  :config (dbx-mode-line-mode 1))
#+end_src

The =python/= directory must stay next to =dbx-el.el=; package-vc keeps the
whole checkout, so nothing else is needed.

* Configuration

Contexts say what you work against.  Without any, dbx uses the profiles
in =~/.databrickscfg= directly.

#+begin_src emacs-lisp
(setq dbx-contexts
      '((:name "dev"  :profile "dev"  :cluster "0612-123456-abcd" :warehouse "1a2b3c4d5e6f7a8b")
        (:name "prod" :profile "prod" :serverless t :warehouse "9f8e7d6c5b4a3f2e"
         :catalog "main" :schema "analytics" :confirm t)))
#+end_src

A project can pick a context in =.dir-locals.el= (only the name; the
definition stays in your init):

#+begin_src emacs-lisp
((nil . ((dbx-project-context . "dev"))))
#+end_src

** Python environment

By default dbx creates and owns one uv environment per Databricks Connect
version under =~/.emacs.d/dbx/venvs/=, matching the cluster's DBR (or
=dbx-serverless-connect-version= for serverless).  It asks before
creating it.  To use your own environment instead (dbx never installs
anything into it):

#+begin_src emacs-lisp
(setq dbx-connect-venv "~/work/project/.venv")
#+end_src

It must contain =databricks-connect= and must not contain =pyspark= or
=pyspark-client=.  =M-x dbx-doctor= checks this.

** Glyphs

Pages and lists show run states as glyphs (=✔ ✘ ⟳ ⊘ ■= ...) in grids
that must line up.  With =dbx-glyph-style= =auto= (the default), each
glyph the frame can't draw exactly one column wide (missing from your
font and taken from a wider fallback font, or ambiguous-width and two
columns wide) is replaced by its ASCII form; the rest stay Unicode.
Grids are aligned with display specs either way.  To keep all
glyphs Unicode, draw them from one font:

#+begin_src emacs-lisp
(dolist (c '(?✔ ?✘ ?⟳ ?○ ?■ ?⊘ ?· ?▲ ?● ?◆ ?◇ ?★ ?▶ ?∅ ?…))
  (set-fontset-font t c "Symbols Nerd Font Mono" nil 'prepend))
(setopt dbx-glyph-style 'auto)    ; re-check the glyphs
;; or force a set: (setopt dbx-glyph-style 'unicode) / 'ascii
#+end_src

M-x describe-char on a glyph shows the font drawing it.

* Usage

=C-c d d= opens the menu.  Global keys under =C-c d=:

| Key   | Command                   | Key   | Command                  |
|-------+---------------------------+-------+--------------------------|
| =d=   | menu                      | =x=   | select context           |
| =o=   | open ID or URL            |       |                          |
| =j=   | find job                  | =J=   | jobs list                |
| =r=   | find run                  | =R=   | active runs              |
| =c=   | find cluster              | =C=   | clusters list            |
| =w=   | find warehouse            | =W=   | warehouses list          |
| =s=   | new SQL editor            | =h=   | query history            |
| =p=   | find pipeline             | =P=   | pipelines list           |
| =b=   | bundle menu               | =g=   | graph for current buffer |
| =z=   | Python REPL               | =!=   | watched runs             |
| =D=   | doctor                    |       |                          |

** Pages and lists

All pages and lists share: =RET= open, =g= refresh, =TAB= fold, =n=/=p=
items, =M-n=/=M-p= sections, =]=/=[= newer/older, =w=/=W= copy id/URL,
=o= browser, =G= graph, =f= watch, =?= actions, =q= quit.

| Buffer    | Keys                                                                         |
|-----------+------------------------------------------------------------------------------|
| Job       | =r= run now, =R= run with parameters, =l= runs, =C= cancel all active runs   |
| Run       | =c= cancel, =R= repair, =x= rerun, =L= task output, =j= job page             |
| Cluster   | =s= start, =S= terminate, =x= restart, =U= use as compute                    |
| Warehouse | =s= start, =S= stop, =U= use for SQL                                         |
| Pipeline  | =s= start, =F= full refresh, =T= refresh tables, =v= validate, =S= stop, =H= history |
| Bundle    | =RET= open resource, =y= YAML definition, =r= run, =v= validate, =l= plan, =d= deploy |
| Graph     | =RET= open node (or click), =t= text/graphics, =m= copy Mermaid, =d= copy DOT |

Destructive actions (cancel, terminate, deploy, destroy, full refresh)
always ask first.  Runs started from Emacs are watched and produce a
desktop notification when they finish.

=C-c d o= (=dbx-open=) opens a page from a bare id or a workspace URL
pasted from Slack or an alert e-mail: jobs, runs, clusters, warehouses
and pipelines, including the legacy =#job/…= forms.  The latest kill is
the default.  A URL whose host belongs to one of your contexts opens in
that context.

Each page and list keeps the context of the buffer it was opened from
(for example a project buffer whose =.dir-locals.el= says =prod=), for
refreshes, actions and the pages opened from it.  The context name is
part of the buffer name: =*dbx job: etl-job [prod]*=.  The same id in
two contexts gets two buffers.

** SQL

In any =sql-mode= buffer enable =dbx-sql-mode= (or use =C-c d s=):

| Key       | Action                      | Key       | Action             |
|-----------+-----------------------------+-----------+--------------------|
| =C-c C-c= | run statement at point      | =C-c C-r= | run region         |
| =C-c C-b= | run buffer                  | =C-c C-k= | cancel             |
| =C-c C-t= | choose warehouse            | =C-c C-s= | catalog and schema |
| =C-c C-l= | row limit (default 2000)    | =C-c C-h= | query history      |

=:name= parameters are prompted for.  Results go to an Org buffer, one
section per run, as pre-aligned Org tables.  There: =n=/=p= results,
=r= re-run, =e= export (CSV/TSV), =c=/=C= copy cell/row, =y= copy table
as TSV, =s= sort by column, =E= make editable.

** Python

=C-c d z= starts the REPL (creating the uv environment if needed).  In
Python buffers enable =dbx-python-mode=: =C-c C-c= buffer, =C-c C-r=
region, =C-M-x= defun, =C-c C-k= interrupt, =C-c C-f= run file,
=C-c C-z= REPL.  =spark=, =sql=, =udf=, =dbutils= and =getArgument= are
predefined.  Interrupt cancels both the local Python code and the Spark
operations it started (by tag).

** Bundles

=dbx-bundle-mode= turns on in YAML files of projects with
=databricks.yml=: Flymake diagnostics from =bundle validate=, and
=C-c C-b= for the bundle menu (summary, graph, validate, plan, deploy,
run, destroy, target).

* Extending

These functions and variables are the public API for user code
(dashboards, favorites, Org links, ...).  Names with a double dash are
internal and may change.

** Contexts

- =(dbx-with-context CONTEXT BODY...)= runs BODY with CONTEXT (a name
  or plist) active.  Calls started in BODY, their callbacks and pages
  opened from them all use it.
- =(dbx-context)= is the active context plist, resolved in this order:
  =dbx-with-context= (CLI callbacks run inside one bound to the context
  of their call), the buffer's own =dbx-buffer-context= (pages and
  lists), =dbx-project-context= (dir-locals), =dbx-current-context-name=,
  the first of =dbx-contexts=.
- =(dbx-context-name &optional CTX)=, =(dbx-context-by-name NAME)=,
  =(dbx-context-for-host HOST)=.
- =dbx-api=, =dbx-api-pages= and =dbx-cli= take =:context=; their
  callbacks run in that context.

** Opening objects

=dbx-job-page=, =dbx-run-page=, =dbx-cluster-page=,
=dbx-warehouse-page= and =dbx-pipeline-page= take =(ID &optional
CONTEXT NO-SELECT)= and return the page buffer.  With NO-SELECT the page
is prepared without being displayed.  =dbx-jobs=, =dbx-runs=,
=dbx-clusters=, =dbx-warehouses= and =dbx-pipelines= take an optional
CONTEXT.  =(dbx-open REF)= opens an id or URL;
=(dbx-parse-object-ref STRING)= only parses it.

** Objects at point and runs

- =(dbx-job-at-point)= returns =(:id ID :name NAME :context CTX-NAME)=
  in job and run pages and in the jobs and runs lists, else nil.
  =(dbx-run-at-point)= returns =(:id :job-id :name :context)= in run
  pages, on runs in job pages and in the runs list.  Neither prompts.
- =(dbx-job-latest-runs JOB-ID N CALLBACK &key CONTEXT ERROR-CALLBACK)=
  fetches the N latest runs without tasks, newest first.
- =(dbx-runs-glyph-strip RUNS)= is the status strip used in the jobs
  list and picker, oldest first.
- =(dbx-watch-run RUN-ID &optional CONTEXT)= watches a run.
  =dbx-run-finished-functions= is called with =(RUN CONTEXT-NAME)= when
  a watched run ends.

** Pages and lists

Derive from =dbx-page-mode= (text pages) or =dbx-list-mode=
(tabulated lists) and use these buffer-local variables:

| Variable / function            | Purpose                                                          |
|--------------------------------+------------------------------------------------------------------|
| =dbx-page-refresh-function=    | no-argument function that fetches and re-renders (=g=)           |
| =dbx-page-active-p=            | non-nil while something runs: refresh every =dbx-page-refresh-active= s |
| =dbx-page-schedule-refresh=    | call after rendering to schedule the next refresh                |
| =dbx-page-refresh-active=, =-idle= | may be set buffer-locally, e.g. to poll a big dashboard less |
| =dbx-page-actions=             | list of =(KEY DESCRIPTION COMMAND)= offered by =?=               |
| =dbx-page-extra-actions=       | global alist =(MODE . ((KEY DESCRIPTION COMMAND) ...))= for =?=  |
| =dbx-list-open-function=       | called with the row id by =RET=                                  |
| =dbx-list-url-function=        | returns the URL of a row id, for =W= and =o=                     |
| =dbx-list-set-entries=         | show entries, keeping the current =/= filter                     |
| =dbx-page-buffer=              | find or create a buffer by =(KIND ID CONTEXT)=                   |
| =dbx-page-rename=              | rename a page after its object, keeping kind and context         |

Row ids may be =(ID . CONTEXT)=: =RET=, =o=, =W= then call the open and
URL functions with ID while CONTEXT is active, and =w= copies ID.  This
lets one list show objects from several workspaces.  =dbx-list-row-id=
and =dbx-list-row-context= read the row at point.

The suffix keys of =dbx-dispatch= are stable, so they can be used as
=transient-append-suffix= anchors.
